พี่ปลา — Senior Engineer ใน startup สาย healthtech เล่าว่าวันหนึ่งที่นักลงทุนขอเดโมระบบ แต่ห้ามใช้ข้อมูลคนไข้จริง โค้ดที่ผูกตรงเข้ากับ MongoDB ทำให้ทีมไม่สามารถสลับไปใช้ข้อมูลปลอมได้ ทั้งทีมต้องอยู่เขียน “ระบบปลอม” กันทั้งคืน หลังคืนนั้นเธอผลักดันให้เกิด “สัญญาการเข้าถึงข้อมูล” ที่ทุก Use Case ต้องเรียกผ่านเท่านั้น ตั้งแต่นั้นการสลับที่เก็บจริง/ปลอมใช้เวลาไม่ถึง 5 นาที “อย่าให้โค้ดธุรกิจรู้จักเทคโนโลยีเก็บข้อมูล — ให้มันรู้จักแค่สัญญา”

ถอดรหัสวิธีคิดของคนสำเร็จ:

  • รวมการเข้าถึงข้อมูลไว้หลัง “สัญญา” (ABC) เดียว — Repository Pattern
  • ซ่อนโครงสร้างภายใน และไม่คืนของที่ภายนอกแก้ไขได้ (Information Hiding)
  • ห่อ “เทคโนโลยีที่เปลี่ยนบ่อย” ด้วย abstraction ที่มั่นคง (Protected Variations)
  • แยก Entity (มีตัวตนด้วย id) ออกจาก Value Object (เทียบด้วยค่า) ให้ชัดเจน

Finding Sandbox: ห้องนิรภัยที่ประตูเปิดทิ้งไว้

ทัศนคติประจำใบงาน: Failure is learning — ผิดหรือถูกไม่สำคัญ นี่คือการทดลองเพื่อเติบโต

พิจารณาโค้ดต่อไปนี้ แล้วสังเกตว่า “ข้อมูลภายใน” รั่วไหลได้อย่างไร

class Student:
    def __init__(self, id: int, email: str):
        self.id = id
        self.email = email


class StudentStore:
    def __init__(self):
        self._students: dict[int, Student] = {}

    def add(self, s: Student) -> None:
        self._students[s.id] = s

    def all(self) -> dict[int, Student]:
        return self._students   # คืนโครงสร้างภายในโดยตรง!


store = StudentStore()
store.add(Student(680001, 'student@example.ac.th'))

data = store.all()
data[680001].email = 'hack@evil.com'   # ข้อมูลจริงพัง!
print(store.all()[680001].email)

1) เหตุใดการแก้ข้อมูลใน data จึงส่งผลถึงข้อมูลภายใน store ทั้งที่ _students ขึ้นต้นด้วย underscore

เพราะตัวแปร data ได้รับการส่งคืนค่าเป็น Reference
เมื่อ _students จะตั้งชื่อแบบ Private ด้วย Underscore แต่เมธอด all() ได้ return self._students

2) คุณจะออกแบบ all() และตัว Entity อย่างไรให้ “คนภายนอกแก้ไขข้อมูลภายในไม่ได้เลย”

ออกแบบให้เป็น Immutable เปลี่ยนแปลงไม่ได้ ใช้ @dataclass(frozen=True) หรือใช้ @property แบบ Read-only
หลีกเลี่ยงการคืนค่า Reference ให้คืนค่าเป็น Deep Copy หรือสร้าง List/Tuple ใหม่ที่เป็น Read-only

3) ลองให้ AI เสนอวิธีป้องกันการแก้ไขข้อมูลภายในมา 3 วิธี แล้วถกกับเพื่อน: วิธีใดน่าเชื่อถือที่สุด และคำตอบของ AI เชื่อถือได้มากน้อยเพียงใด (ฟังเพื่อนให้จบก่อนสรุปนะ)

1.mmutable Objects / Frozen Data Classes: กำหนดให้ Entity เป็นแบบอ่านอย่างเดียวด้วย @dataclass(frozen=True)
2.Defensive Copying (สำเนาป้องกัน): เมธอด all() ทำการสำเนาข้อมูลชุดใหม่ (Copy / Deepcopy) ก่อนส่งออกไปภายนอกเสมอ
3.Read-Only Views / DTO Mapping: ส่งออกข้อมูลในรูปแบบ Data Transfer Object (DTO) หรือ MappingProxyType / Tuple
การผสานวิธีที่ 1 (Immutable Entity) ร่วมกับวิธีที่ 3 (DTO/Tuple View) เพราะป้องกันได้ตั้งแต่ระดับ Type Definition
📦 กล่องความรู้เสริม (อ่านเฉพาะเมื่อจำเป็น):
  • Repository Pattern: รวมการเข้าถึงข้อมูลไว้หลัง “สัญญา” (ABC) ทำให้ Use Case ไม่ต้องรู้จักเทคโนโลยีการจัดเก็บ
  • DIP: Use Case พึ่งพา abstraction (UserRepository) ไม่ใช่ implementation
  • Information Hiding: ซ่อนโครงสร้างภายใน (private dict) และคืน “สำเนา” เพื่อป้องกันภายนอกแก้ไข
  • Protected Variations: ห่อหุ้ม “เทคโนโลยีจัดเก็บ” (จุดที่เปลี่ยนบ่อย) ด้วย ABC ที่มั่นคง
  • Entity vs Value Object: Entity มี identity (id) เช่น User; Value Object เทียบด้วยค่าและมัก immutable เช่น Email
  • frozen dataclass: @dataclass(frozen=True) ทำให้แก้ไขฟิลด์หลังสร้างไม่ได้ (FrozenInstanceError)

ส่วนที่ 1: อ่านแผนภาพแล้วตอบคำถาม (10 คะแนน)

1) «ABC» UserRepository ทำหน้าที่อะไรในระบบ และเหตุใดต้องแยก “สัญญา” ออกจาก implementation 2 คะแนน

ทำหน้าที่เป็น Interface หรือ Abstract Base Class ที่กำหนดเมธอดมาตรฐานในการเข้าถึงและจัดการข้อมูล User
เหตุผลเพราะเพื่อให้เป็นไปตามหลัก Dependency Inversion Principle (DIP) และ Loose Coupling ทำให้โค้ดส่วน Business Logic

2) ลูกศร “implements” จาก InMemoryUserRepository ชี้ไปยัง UserRepository หมายถึงอะไรในเชิงโค้ด Python 2 คะแนน

หมายถึง คลาส InMemoryUserRepository ทำการสืบทอด (Inherit) มาจากคลาส UserRepository
และเขียนทับ (Override / Implement) การทำงานจริงของทุก Abstract Method ที่กำหนดไว้ใน UserRepository

3) «dataclass frozen» ที่กำกับคลาส User หมายความว่าอย่างไร และ User จัดเป็น Entity ต่างจาก Value Object อย่างไร 2 คะแนน

หมายถึง การใช้ @dataclass(frozen=True)ซึ่งทำให้อ็อบเจกต์เป็น Immutable ความต่างระหว่าง Entity กับ Value Object
User เป็น Entity เพราะมี id เป็นตัวระบุตัวตนเฉพาะต่างจาก Value Object ที่ไม่มี id และเทียบความเท่ากันด้วยค่าของข้อมูลทั้งหมดภายในอ็อบเจกต์

4) เมธอด find_by_id คืนค่าเป็น “User or None” การคืน None สื่อความหมายว่าอย่างไร 1 คะแนน

ค้นหาข้อมูลไม่พบ หรือไม่มี User ที่ตรงกับ id ที่ระบุอยู่ในระบบ

5) ลูกศร “stores” จาก InMemoryUserRepository ไปยัง User หมายถึงอะไร และใช้โครงสร้างข้อมูลใดในการเก็บ 1 คะแนน

หมายถึงคลาส InMemoryUserRepository ทำหน้าที่เก็บรวบรวมและถือครองอ็อบเจกต์ User ไว้ในหน่วยความจำ (In-Memory)

6) หากในอนาคตต้องการเปลี่ยนไปเก็บข้อมูลในฐานข้อมูล MySQL โค้ดส่วนใดต้องเปลี่ยนแปลงบ้าง 2 คะแนน

สร้างคลาส Implementation ใหม่ เช่น MySQLUserRepository ที่สืบทอดจาก UserRepository (implements UserRepository)
ไม่ต้องแก้คลาส UserRepository และคลาส User ไม่จำเป็นต้องแก้ไข รวมถึงโค้ดส่วน Use Cases/Business Logic ไม่ต้องเปลี่ยนแปลง

ส่วนที่ 2: วิเคราะห์โค้ด (10 คะแนน)

from abc import ABC, abstractmethod
from dataclasses import dataclass


@dataclass(frozen=True)
class User:
    id: int
    email: str


class UserRepository(ABC):
    @abstractmethod
    def save(self, user: User) -> None: ...

    @abstractmethod
    def find_by_id(self, user_id: int) -> User | None: ...

    @abstractmethod
    def all(self) -> list[User]: ...


class InMemoryUserRepository(UserRepository):
    def __init__(self):
        self._users: dict[int, User] = {}

    def save(self, user: User) -> None:
        self._users[user.id] = user

    def find_by_id(self, user_id: int) -> User | None:
        return self._users.get(user_id)

    def all(self) -> list[User]:
        return list(self._users.values())


repo = InMemoryUserRepository()
repo.save(User(680001, "student@example.ac.th"))
repo.save(User(680002, "student2@example.ac.th"))

student = repo.find_by_id(680001)
print(student)
print(f"จำนวนนักศึกษาทั้งหมด: {len(repo.all())} คน")

1) เหตุใดเมธอด all() จึงใช้ list(self._users.values()) แทนการคืนโครงสร้างภายในโดยตรง ป้องกันความเสี่ยงใด 3 คะแนน

พื่อซ่อนโครงสร้างข้อมูลภายใน (Information Hiding / Encapsulation) และแปลงข้อมูลจาก dictionary values
ป้องกันไม่ให้โค้ดภายนอกเข้าถึงหรือแก้ไขโครงสร้างข้อมูลภายในของ Repository ลดความเสี่ยงเรื่อง Side Effects / Data Mutation โดยไม่ผ่าน Repository

2) การเรียก repo.find_by_id(999999) ให้ผลลัพธ์เป็นอะไร และโค้ดบรรทัดใดรับผิดชอบ 2 คะแนน

ได้ค่า None และ return self._users.get(user_id)

3) หาก save ผู้ใช้ที่มี id ซ้ำกับข้อมูลเดิมจะเกิดอะไรขึ้น เพราะเหตุใด 3 คะแนน

ข้อมูล User เดิมที่มี id ตรงกันจะถูก เขียนทับ (Overwrite/Update) ด้วยข้อมูล User ใหม่
พราะใน Python เมื่อกำหนดค่าให้กับ dictionary key ที่มีอยู่แล้วผ่านคำสั่ง self._users[user.id] = user ตัว dictionary

4) หากพยายามแก้ไข user.email หลังสร้างวัตถุแล้วจะเกิดอะไรขึ้น เพราะเหตุใดจึงออกแบบเป็น frozen 2 คะแนน

จะเกิดข้อผิดพลาด FrozenInstanceError
เพื่อทำให้ข้อมูลเป็น Immutable ช่วยป้องกันการแก้ไขข้อมูลโดยไม่ตั้งใจและรับประกันความถูกต้องของสถานะข้อมูล

ส่วนที่ 5: สะท้อนคิดเชิงออกแบบ OOAD (6 คะแนน)

1) Repository Pattern ช่วยลด coupling ระหว่าง Use Case กับเทคโนโลยีการจัดเก็บข้อมูลอย่างไร 2 คะแนน

ช่วยตัดการพึ่งพาโดยตรง (Decoupling) โดยให้ Use Case เรียกใช้งานผ่าน Interface (Abstraction) เท่านั้น
ทำให้ Business Logic ไม่ต้องสนใจว่าข้อมูลจะถูกจัดเก็บไว้ที่ใดหรือด้วยเทคโนโลยีอะไร ส่งผลให้แก้ไขหรือสลับเปลี่ยน Data Source

2) “จุดที่เปลี่ยนแปลง” ในข้อนี้คืออะไร และการออกแบบนี้ปกป้องระบบด้วย Protected Variations อย่างไร 2 คะแนน

วิธีการและเทคโนโลยีในการจัดเก็บข้อมูล (Storage Mechanism / Implementation) เช่น การเปลี่ยนจาก InMemory

1) ในโปรเจกต์ Python ถัดไปของคุณ จุดใดคือ “การเข้าถึงที่เก็บข้อมูลโดยตรง” ที่จะกลายเป็นระเบิดเวลาเมื่อเปลี่ยนเทคโนโลยี และคุณจะห่อมันด้วย ABC อย่างไร
