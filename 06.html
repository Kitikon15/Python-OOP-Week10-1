1.Shared Utility / Module เขียนฟังก์ชันหรือ Value Object กลางไว้ในโฟลเดอร์ประเภท utils หรือ core
2.Custom Database Data Type/Domain-Driven Value Object Type พร้อม Trigger/Constraint or ODM/ORM Model
3.Centralized Identity & Access Management Service แยก Service จัดการผู้ใช้และข้อมูลประจำตัวออกมาเป็นระบบกลาง
วิธีที่น่าเชื่อถือและทำได้จริงที่สุดในตอนนี้: วิธีที่ 1 (Shared Utility/Value Object) เพราะเริ่มทำได้ทันที ไม่ซับซ้อน ช่วยแก้ปัญหาเรื่อง .strip() และ .lower()
📦 กล่องความรู้เสริม (อ่านเฉพาะเมื่อจำเป็น):
  • Value Object: วัตถุที่ไม่มี identity เทียบด้วยค่า และรวมค่า + กฎตรวจสอบไว้ในที่เดียว
  • Immutability: สร้างแล้วแก้ไขไม่ได้ — ค่าที่ validate แล้วไม่ถูกทำให้เสียภายหลัง
  • Static Factory: บังคับ validate ก่อนสร้างวัตถุ (fail fast) เช่น Email.from_string()
  • Normalization: strip + lower-case เพื่อให้ “ค่าเดียวกัน” ถูกมองว่าเหมือนกันทั้งระบบ
  • Python frozen dataclass: @dataclass(frozen=True) + __post_init__ + object.__setattr__ เพื่อ normalize ค่าในวัตถุที่แก้ไขไม่ได้
  • DRY: กฎเขียนครั้งเดียว ใช้ได้ทุกแห่ง ไม่ต้อง copy-paste การตรวจสอบ

ส่วนที่ 2: วิเคราะห์โค้ด (10 คะแนน)

import re
from dataclasses import dataclass


@dataclass(frozen=True)
class Email:
    value: str

    def __post_init__(self) -> None:
        normalized = self.value.strip().lower()
        if not re.fullmatch(r"[^@\s]+@[^@\s]+\.[^@\s]+", normalized):
            raise ValueError("Invalid email address.")
        object.__setattr__(self, "value", normalized)

    @classmethod
    def from_string(cls, value: str) -> "Email":
        return cls(value)

    def equals(self, other: "Email") -> bool:
        return self.value == other.value

    def __str__(self) -> str:
        return self.value


student_email = Email.from_string("Student@Example.ac.th ")
print(str(student_email))

another_email = Email.from_string("student@example.ac.th")
print(student_email.equals(another_email))

1) ผลลัพธ์ของ Email.from_string("Student@Example.ac.th ") คืออะไร จงอธิบายการทำงานทีละขั้นตอน 3 คะแนน

ได้ออบเจกต์ Email ที่มีค่าแอตทริบิวต์ value = "student@example.ac.th"
เมธอด from_string รับค่าสตริงเข้ามา แล้วส่งต่อไปสร้างอินสแตนซ์ผ่านคอนสตรักเตอร์ cls(value)
เมื่อสร้างอินสแตนซ์เสร็จ ระบบจะเรียกเมธอด __post_init__() อัตโนมัติ
self.value.strip().lower() ทำการตัดช่องว่างด้านหลังและแปลงตัวอักษรทั้งหมดเป็นตัวพิมพ์เล็ก ได้เป็น "student@example.ac.th"

2) การเรียก Email.from_string("student@invalid") จะเกิดอะไรขึ้น เพราะเหตุใด 2 คะแนน

เกิด Error ประเภท ValueError: Invalid email address. และระบบหยุดทำงานทันที
เพราะรูปแบบ Regex กำหนดไว้ว่าหลังเครื่องหมาย @ จะต้องมีจุดและตามด้วยโดเมน

3) เหตุใด equals ระหว่าง "Student@Example.ac.th " กับ "student@example.ac.th" จึงคืนค่า True 3 คะแนน

เพราะทั้งสองตัวถูกสร้างผ่านคลาส Email ซึ่งมีขั้นตอน Normalize ข้อมูลใน __post_init__() เหมือนกัน
ตัวแรก "Student@Example.ac.th " ถูกตัดช่องว่างและแปลงเป็นตัวพิมพ์เล็กจนเหลือ "student@example.ac.th"

4) หากพยายามแก้ไข student_email.value = "x@y.z" จะเกิดอะไรขึ้น เพราะเหตุใดจึงออกแบบเป็น frozen 2 คะแนน

ตัวอย่างปัญหา หากโมดูล A ส่งออบเจกต์ให้อีกฟังก์ชัน แล้วฟังก์ชันนั้นแอบแก้เป็น invalid-email

3) Email สามารถนำไปใช้ร่วมกับ Use Case อื่น (เช่น RegisterUserService ข้อ 10) ได้อย่างไร และดีอย่างไร 2 คะแนน

นำไปใช้โดยกำหนดให้ Type ของพารามิเตอร์รับค่าเป็น Email แทน str ธรรมดา เช่น def register(email: Email)
ข้อดีคือ Use Case ไม่ต้องรับผิดชอบการเช็กอีเมลซ้ำซ้อนและการันตีได้ 100% ว่าค่าที่เข้ามาในเซอร์วิสสะอาดและถูกต้องเสมอ

Future นำสิ่งค้นพบไปสู่อนาคต

1) ในโปรเจกต์ Python ถัดไปของคุณ ข้อมูลใดคือ “อีเมลคนใหม่” (มีกฎตรวจสอบและถูกเขียนซ้ำกระจายอยู่) และคุณจะเปลี่ยนมันให้เป็น Value Object อย่างไร

ข้อมูลคือ เบอร์โทรศัพท์ที่มักมีปัญหาคนกรอกติดขีด เว้นวรรค หรือมีรหัสประเทศ +66 กระจายอยู่หลายโมดูล
เปลี่ยนเป็น Value Object โดยใช้ @dataclass(frozen=True) พร้อมตัดขีด/ช่องว่าง

2) เขียน commitments สั้น ๆ 2 ข้อ เกี่ยวกับนิสัย “validate ครั้งเดียว ณ จุดสร้าง และห้ามแก้ไขภายหลัง” ที่คุณจะนำไปใช้จริง

1. แปลง String ดิบเป็น Value Object ตั้งแต่จุดรับเข้า (API / Form) เพื่อการันตีว่าข้อมูลที่ส่งต่อในระบบ
2. กำหนด frozen=True ให้กับทุกคลาสที่เป็น Value Object เสมอ เพื่อตัดปัญหา Side Effects และป้องกันการแอบเปลี่ยนค่ากลางทาง
🪞 มุมสะท้อนคิดของโค้ช:

ชมความพยายามของตัวเอง 1 เรื่อง แล้วบันทึก “คำถามที่ยังค้างอยู่ในหัวคุณ” เกี่ยวกับ Value Object หรือ immutability

ภูมิใจที่ทำความเข้าใจหลักการ OOAD เรื่อง Value Object และ Immutability ได้เห็นภาพชัดเจนขึ้น
หากระบบต้องรองรับข้อมูลจำนวนมหาศาล (หลักแสน-ล้านเรคอร์ด) การสร้างออบเจกต์ใหม่แทนการแก้ค่าเดิมจะกิน Memory และส่งผลต่อ Performance มากน้อยแค่ไหน
